# 技術決策紀錄

這份文件只記錄**已經拍板、且事後改動成本很高**的技術決定。每項包含決定、理由、以及「什麼情況下該重新檢討」。

設計問題請看〈[待決事項](OPEN-QUESTIONS.md)〉，工時與範圍請看〈[開發里程碑](11-roadmap.md)〉。

---

## TD-01・渲染器：Forward+

| | |
|---|---|
| 決定 | `renderer/rendering_method = forward_plus` |
| 狀態 | 已套用至 `trio-project/project.godot` |

**理由**：目標平台是 PC / Steam，美術方向是低多邊形卡通風與少量光源，離 GPU 瓶頸很遠。Compatibility 渲染器在後處理、compute 與部分螢幕空間效果上有明確限制，而**為某一渲染器寫的 shader 無法無痛搬到另一個**——水面、腐化溶解、命中閃白、描邊全部綁在這個選擇上。用 Compatibility 換到的效能，換不回損失的表現力。

**同時移除**：`rendering_device/driver.windows = "d3d12"`。該設定在 Compatibility 下無效，在 Forward+ 下會強制走 D3D12 後端；預設的 Vulkan 更穩，需要時再開。

**重新檢討的觸發條件**：M2 實測分屏雙渲染在目標最低規格上掉到 60 FPS 以下。屆時的選項是降 Mobile 渲染器，而不是回 Compatibility。

## TD-02・網路權威模型：自己的角色 client 權威，其餘 host 權威

| 項目 | 權威方 |
|---|---|
| 自己角色的移動與跳躍 | **該玩家的 client** |
| 抓取判定（重量規則）、投擲結果 | host |
| 傷害、血量、倒地狀態 | host |
| 敵人 AI 與位置 | host |
| 場景物理物件（原木、石頭、礦車） | host |
| 疊高狀態機（成立、順序、潰散） | host |
| 章節進度、控制點、寶箱 | host |

**理由**：三人合作 PvE，作弊沒有意義。完整 server authority + 預測回滾能換到的只有抗延遲，代價是 100 小時以上的額外工程，對本作是過度工程。反之純 server authority 無預測會產生輸入延遲，與〈[戰鬥與敵人](05-combat.md)〉的 Overcooked 回饋速度基準直接衝突。

**實作硬規則**：

- 抓取是 **request → host 驗證重量階梯 → 廣播結果**，客戶端絕不自行決定抓取成立
- 客戶端上的場景物理物件關閉物理運算，只做插值跟隨 host 的 transform
- 客戶端可以樂觀播放攻擊動畫與命中特效，但**扣血一律等 host**

**重新檢討的觸發條件**：M0 的延遲測試（見 TD-10）顯示 client 權威移動導致隊友位置飄移到影響抓取與疊高。

## TD-03・傳輸層：開發用 ENet，上市用 Steam relay

**決定**：M0–M3 使用內建 `ENetMultiplayerPeer`；上市前換成 Steam 的 P2P / relay（`SteamMultiplayerPeer`）。

**理由**：〈[開發里程碑](11-roadmap.md)〉M4 已指出「兩個朋友連不上線」會直接變成退款。裸 ENet 在真實家用網路（雙層 NAT、CGNAT）下的連線失敗率不可接受，這個問題的解法是 Steam 的 NAT 打洞與中繼伺服器，不是自己寫連線碼。

**現在就要做的事**：把 peer 的建立與銷毀**全部收在單一 autoload**（`NetworkService`）裡，遊戲其他部分只呼叫 `host_game()` / `join_game()`，不直接碰 `MultiplayerPeer`。這樣未來換傳輸層是改一個檔案，而不是全專案搜尋。

## TD-04・玩家身分抽象：一個 peer ≠ 一個玩家

**決定**：從 M0 第一行程式開始，玩家身分即為獨立資料結構，不得用 `peer_id` 當作玩家識別。

```
PlayerSlot {
    slot_id            # 0..2，隊伍中的位置
    peer_id            # 哪台機器（本地 AI 為 host 的 peer_id）
    input_device       # 哪個輸入裝置（同一 peer 可有多個）
    is_ai              # 是否由 AI 接管
    possessed_character # 目前操控哪隻角色
}
```

**理由**：這一層同時撐起三件**已經寫進設計文件**的功能——

| 功能 | 出處 | 沒有這層會怎樣 |
|---|---|---|
| 2 人本地分屏 + 1 人線上 | 〈[連線、營地與分屏](08-multiplayer-camp.md)〉 | 同一 peer 兩個玩家無法表達 |
| AI 夥伴補位、玩家中途接手 | 〈[開發里程碑](11-roadmap.md)〉Must | 接手＝換 peer，狀態全斷 |
| 營地換角色（possess 交換） | 〈[連線、營地與分屏](08-multiplayer-camp.md)〉 | 身分與角色綁死，無法交換 |

**這是唯一一件「功能延到上市後、但位子現在就得留」的事。** 現在寫死只省數小時，兩年後拆是數十小時，且會動到連線核心。

**注意**：本項不代表要在 M0 實作分屏。M0 只需要讓 `PlayerSlot` 存在且正確，分屏仍照〈開發里程碑〉延到上市後更新。

## TD-05・疊高同步：邏輯附掛，不做網路化剛體堆疊

**決定**：疊高成立時，上層角色改為**邏輯附掛**於下層——其 transform 由「底座 transform + 本地 offset」推導，整柱以單一實體同步。上層的移動輸入轉為鏡頭與掙扎輸入。潰散＝解除附掛 + 施加分離衝量 + 全員 ragdoll。

**理由**：網路化的剛體堆疊在任何引擎上都極難做穩，Jolt 也只是讓單機堆疊更穩，不解決同步問題。改成附掛後，全案最高風險項從「物理同步問題」降級成「狀態機 + 父子關係問題」，後者是可以做對的。

**這與設計文件一致**：〈[核心系統](04-systems.md)〉本來就寫「底層移動時上層跟隨」「順序由重量決定」——上層是乘客，不是共同施力者。附掛模型正好是這句話的直接實作。

**Jolt 的職責**：只負責潰散那一瞬間之後的表現，以及非疊高狀態下的一般物理。

**驗收**：見 TD-10。

## TD-06・Ragdoll 同步：狀態與根位置同步，骨骼各機自算

**決定**：

| 同步 | 不同步 |
|---|---|
| 進入／離開 ragdoll 的狀態切換 | 每根 `PhysicalBone3D` 的 transform |
| 觸發當下的衝量（方向與大小） | 骨骼的模擬過程 |
| host 權威的**根位置** | — |

**理由**：逐骨同步的頻寬與抖動都不可接受。三台機器上手腳擺的姿勢略有差異完全無妨——那反而符合〈[核心定位](01-overview.md)〉的「事故就是內容」。

**但根位置必須是 host 權威**：「你倒在哪」決定隊友能不能扶到你（〈[核心系統](04-systems.md)〉倒地救援）。若各機自算根位置，會出現「我明明站在他旁邊卻扶不到」這種最傷體驗的 bug。

**已知難點**（列入〈[美術管線](12-art-pipeline.md)〉的 40–60 小時內）：離開 ragdoll 時要擷取當下姿勢，在 0.2–0.3 秒內混合到起身動畫首幀。直接切回站姿會「啪」地彈回去，是最破壞喜劇感的畫面。另外 Godot 的 Create Physical Skeleton 一鍵產物必定抽搐，碰撞形狀與關節角度限制全部要手調——這 40–60 小時大半花在手調，不是寫程式。

**實作結果（2026-08）**：`scripts/player/ragdoll.gd` 從人形骨架推導出 13 根實體骨，不用編輯器的 Create Physical Skeleton——那是綁死單一模型的一次性產物，這裡的角色會一直換。

TD-06 預期的「一鍵產物必定抽搐」沒有發生，因為刻意做了三件事：只模擬 13 根主要骨頭（脖子、手掌、腳趾全部略過，Godot 會自動往上找最近的實體骨當關節父節點）、手肘與膝蓋用 HINGE 而不是 CONE、每個 CONE 都給擺幅上限。實測位移在 4.6 秒內衰減到 **0.000** 且停住，沒有顫抖。

擊退的衝量給每一根骨頭並乘上各自質量（不是只推髖部），整具身體才會一起飛——實測 (5, 4, 2) 的衝量飛出 4.4 公尺後躺平。只推髖部的話其餘部位會拖住它，只移動 6 公分。

根位置照 TD-06 的要求走：倒地時本體的位置跟著布娃娃的髖部，實測兩者完全同步，所以「你倒在哪」與畫面一致，扶起判定不會落在原地。

**尚未做**：TD-06 點名的難點——離開布娃娃時擷取當下姿勢、在 0.2–0.3 秒內混合到起身動畫首幀。現在是直接切回動畫，會「啪」地彈一下。那個混合要看得到畫面才調得動。

## TD-07・骨骼命名：採用 Godot 的 SkeletonProfileHumanoid

**決定**：不自創命名規範。所有角色一律使用 Godot `SkeletonProfileHumanoid` 的骨骼命名與階層，import 時以 `BoneMap` 重定向。

**理由**：〈[美術管線](12-art-pipeline.md)〉已決定全角色擬人兩足。既然如此，採用標準人形骨架等於免費打開整個現成人形動畫庫（Mixamo 等）可供 retarget。單人開發者的 20 支共用動畫，能重定向現成的就不該自己做。

**主要骨骼**（完整清單以 Godot 的 profile 為準）：

```
Root / Hips / Spine / Chest / UpperChest / Neck / Head
LeftShoulder  / LeftUpperArm  / LeftLowerArm  / LeftHand
RightShoulder / RightUpperArm / RightLowerArm / RightHand
LeftUpperLeg  / LeftLowerLeg  / LeftFoot  / LeftToes
RightUpperLeg / RightLowerLeg / RightFoot / RightToes
```

**角色專屬骨鏈**（長頸鹿的脖子、豬的耳朵、貓的尾巴等）掛在 profile 之外，不參與重定向，由角色專屬動畫或 secondary motion 驅動。

**Meshy prompt 需求**：T-pose、關節處有 edge loop、5,000–15,000 三角面（見〈美術管線〉資產規格）。

## TD-08・不使用 Root Motion

**決定**：角色位移完全由程式碼計算，動畫只負責視覺表現。

**理由**：Root motion 讓位移量來自動畫曲線，與網路預測、client 權威移動（TD-02）、以及疊高附掛（TD-05）全部衝突。動畫與移動速度的匹配用調整播放速率解決，不用 root motion。

**例外**：無位移需求的過場與情境動作（開寶箱、儀式）可使用，因為那些狀態下角色本來就不接受移動輸入。

## TD-09・Shader：排在 M1 之後，兩項做法先定

**決定**：M0 的 shader 工作量為零。M1 只做兩支：命中閃白、角色描邊。水面、腐化溶解、圖騰發光、合體特效全部排到 M2。

**理由**：shader 有即時的成就感，是單人開發最容易提前開工的項目，然後手感原型永遠沒開始。〈[開發里程碑](11-roadmap.md)〉M1 的驗收標準是「朋友有沒有笑」，那件事不需要任何 shader。

**兩項現在就定的做法**：

| 項目 | 做法 | 理由 |
|---|---|---|
| 角色描邊 | **Inverted hull**——第二個 material pass，`cull_front` + 沿法線外推 | 螢幕空間邊緣偵測在分屏雙視口下要跑兩次；inverted hull 是幾何的一部分，對分屏天然免費 |
| 命中閃白 | **`instance uniform`**，以 `GeometryInstance3D.set_instance_shader_parameter()` 驅動 | 〈[戰鬥與敵人](05-combat.md)〉要求閃白 0.05 秒且頻率極高，複製材質做切換會造成大量 material 切換 |

### 實作狀態

**角色描邊：已完成，照原案做。** `scripts/shaders/outline.gdshader`（`cull_front` + 沿法線外推 + `unshaded`），共用材質由 `scripts/core/outline.gd` 統一提供，掛在角色與泥偶的 `next_pass`。外推量乘上到鏡頭的距離，所以描邊在畫面上遠近一樣粗——這是「半畫面尺寸下仍須可辨識」那條要求的直接解法。誰有描邊：**會動的東西**（角色、敵人）。場景方塊沒有，全部都描會變成線稿。

**命中閃白：改用 `StandardMaterial3D.emission`，沒有照原案的 `instance uniform` 做。**

原案要避免的成本是「複製材質做切換」，但實際實作出來的不是那樣：`character_visual.gd` 的 `_cache_materials()` 在**載入時**把每隻角色的材質複製一份（固定次數，之後不再變動），閃白只是改那份材質上的 `emission` 數值——那是更新 uniform，不是切換材質。這一格想避免的成本，現在的寫法本來就沒有付。

改成 `instance uniform` 反而要付代價：instance uniform 只能宣告在 `ShaderMaterial` 上，所以得把匯入的 `StandardMaterial3D` 整個換成手寫 shader。這三隻模型只有一張 albedo、沒有法線與 ORM 貼圖，技術上做得到，但那等於為了一個目前沒有成本的問題去重寫角色的主材質。

**回頭改的條件**：真的量到 material 切換出現在 profiler 上，或是 M2 要做卡通渲染而必須自己寫角色的主材質時——那時 instance uniform 是順手的，不是額外的。

## TD-10・M0 驗收標準補上延遲測試

**原標準**（〈[開發里程碑](11-roadmap.md)〉）：三台機器連線，疊成三層走動 30 秒不崩、不抖、不穿模。

**補充**：上述測試必須在 **80–150 ms 延遲 + 1% 丟包**的條件下重跑一次才算通過。

**理由**：區網測試幾乎一定會過，然後上市炸掉。撐不住的話 M0 就是失敗——而那正是你花三個月要買到的答案。

**實作（2026-08）**：改成遊戲內建，不用 `clumsy` / `tc netem`。那些要每台測試機各自安裝設定，朋友幫忙測的時候不會想弄，結果就是永遠只有區網成績。

`scripts/net/lag_peer.gd` 是一層 `MultiplayerPeerExtension`，包住 `ENetMultiplayerPeer`：收到的封包壓上到期時間排隊，延遲加 ±25% 抖動（固定延遲比真實網路好對付太多）。大廳有下拉選單，命令列是 `--lag=80 --loss=0.01`。

**只丟 unreliable 的封包。** reliable 的 ENet 自己會重送，在這裡丟掉它測到的是「重送機制有沒有壞」，不是「遊戲在丟包下好不好玩」。

實測（headless，RPC 來回時間，各約 110 個樣本）：

| 下拉的檔位 | 實測來回中位數 | 等效單邊 |
|---|---|---|
| 關閉 | 7.0 ms（loopback） | — |
| 一般 80 ms | 179.6 ms | ~90 ms |
| 惡劣 150 ms | 338.1 ms | ~169 ms |

**實測值比設定值高一點，是刻意的。** 為了保住 ENet reliable 通道的先進先出，
每條通道的放行時間單調不遞減——抖動因此只會往後推、不會往前拉，一串封包下來
會累積約 +6 ms／跳的偏差。方向是偏嚴不偏鬆，對驗收而言是安全的：
「一般」那一檔的等效單邊 90 ms 仍落在 TD-10 要求的 80–150 ms 區間內。

丟包實測（各送 300 個）：

| 設定 | unreliable 抵達 | reliable 抵達 |
|---|---|---|
| 0 | 100.0% | 100.0% |
| 5% | 96.0% | 100.0% |
| 20% | 78.0% | 100.0% |

寫這一層踩到三個坑，都不會有明顯的錯誤訊息：
1. `get_packet_peer()` 的合約是**下一個要讀的封包**，不是剛讀完的（peek 語意）。
2. `peer_connected` / `peer_disconnected` 是 peer 自己發的訊號，不是靠封包傳的——外包層要自己轉發，否則上層永遠不知道有人連進來。
3. `get_packet()` 會把封包彈出佇列，中繼資料（peer / channel / mode）必須**先**讀完再取資料。
4. **每個封包獨立抖動會打亂順序**，而 ENet 的 reliable 通道保證順序。沒防這一手時，
   客戶端在 80 ms 之下會噴「ID 1 not found in cache of peer 1」——同步封包跑到了
   生成封包前面。那是模擬器的錯，不是遊戲的錯，但看起來一模一樣，
   很容易誤判成遊戲在延遲下壞掉。

**驗收數字仍未取得**：三人在 80 ms／1% 之下疊高走動 30 秒，還沒有真人跑過。大廳的疊高計時會自動記錄，而且那一行會把當下的網路條件一起寫出來——截圖就是證明。

## TD-11・站立表演用程序化姿態層，不等美術補 idle

**決策**：角色的待機表演（呼吸、重心擺動）、看向、以及戰士／弓手／法師的姿態差異，全部由 `scripts/player/procedural_pose.gd` 這一層程式產生，掛在 `Skeleton3D` 底下的 `SkeletonModifier3D`。手刻動畫只負責移動與單次動作（走、跑、攻擊、受擊）。

**理由**：

1. **現實**：Meshy 一次只生一支動畫，目前三隻角色都只有 `walk`，沒有 `idle`。站著不動時如果不做事，畫面上就是三尊雕像。等美術補齊要等到 M2。
2. **辨識度不必靠動畫**。三隻角色共用同一套人形骨架，職業差異用「每根骨頭一組角度偏移」就能做出來——戰士手臂外張前傾、弓手側身收肩、法師挺胸收手。這是資料不是程式，寫在 `character_roster.gd` 的 `pose` 欄位，改一個數就能調。
3. **省下的不只是動畫**。三個職業 × 待機 = 三支動畫要生、要正規化、要對骨架、要進版控。程序化的版本是一個檔案加三組數字。

**約定**：所有角度都是**角色空間**的尤拉角（度）：X 正 = 抬頭／後仰、Y 正 = 向左轉、Z 正 = 往角色右手邊倒。這一層不依賴骨骼自己的朝向，換模型不必重調軸向。

**權衡**：程序化做得出「活著」，做不出「表演」。真正有個性的待機動作（法師轉法杖、弓手撥弦）還是要手刻，那是 M2 的事。這一層是地板，不是天花板。

**不同步**：純表演，每台機器各自算。角色位置本來就同步，算出來的結果一致，不值得為了轉頭再開一條網路欄位。

## TD-12・循環動作外購，戰鬥動作生成

**決策**：`idle` / `walk` / `run` 從 Mixamo（或任何共用同一套 rig 的動作庫）取得，走既有的正規化管線併成一支 GLB；`attack1`–`attack3`、`attack_dash`、`attack_air`、`hurt`、`death` 由 `scripts/player/motion_forge.gd` 在載入時生成。

**理由**：

1. **判定窗口只有 0.08 秒。** `CombatSpec.COMBO` 的 `light_1` 是 windup 0.08 / active 0.08 / recovery 0.16。現成動畫要對上這個窗口得逐支手動重新計時，而且每調一次手感就要全部重對。生成的片段時間軸直接從 CombatSpec 算——出手那一格永遠正好是 `windup` 結束、判定打開的那一刻，不可能飄。實測：`attack1` 長度 0.3200 秒、關鍵影格落在 0 / 0.068 / **0.080** / 0.160 / 0.320。
2. **循環動作反過來，動捕明顯較好。** 走路的重心轉移、落地的緩衝，程式算得出「有在動」，算不出「有重量」。這種要靠現成資料。
3. **職業辨識度不必額外買。** 三隻共用同一套人形骨架，出手姿勢寫成資料（`motion_clips.gd`）就能分出豬過頂重砸、貓抽射、蛙前推。加上 TD-11 的程序化姿態層，三隻的靜止與出手都認得出來。

**生成的片段不烘進 GLB**，在載入時建成 `AnimationLibrary` 掛進 `AnimationPlayer`。烘死的檔案不會跟著調過的數字走，那正好違背上面第 1 點。

**角度約定集中在 `bone_space.gd`**：角色空間的尤拉角，X 正＝抬頭、Y 正＝向左轉、Z 正＝往右手邊倒。程序化姿態層與生成動畫共用同一份換算，姿勢資料兩邊通用。

### 實作狀態

**`idle` / `run` / `sprint` 目前也是生成的，不是外購的。** 上面寫「循環動作
外購」，但 Meshy 只給了 `walk`，而動捕庫還沒接。所以現況是：

- `idle` 由 `MotionClips.IDLE` 生成（逐職業的持械站姿）
- `run` / `sprint` 是把 `walk` 繞著每條軌自己的平均姿勢外插放大出來的
  ——**落腳的時機來自買來的那支**，這正好保住了上面第 2 點在意的東西
  （重心轉移與落地緩衝算不出來，但這裡沒有重算，是沿用）

換句話說第 2 點的精神還在，只是還沒買到第二支。真的接上動捕庫之後，
`_clip()` 的關鍵字比對會自動改用美術補進來的那一支，程式不必動。

**軀幹的 Y 是揮擊前後方向的真正來源**，比手臂角度還關鍵：蓄力時 Y 負（右肩拉到後面）、出手時 Y 正（右肩推出去）。正負顛倒會變成「蓄力時手往前伸、出手時往後縮」，而且從數字上看不出來——要量手掌相對髖部的軌跡才會現形。三隻角色的資料都是這樣驗過的。

## TD-13・腳滑：先把播放速度算對，再用鎖腳收尾；貼地 IK 等有斜面再說

**決定**：腳滑分兩件事處理。第一件是**把三個各自為政的猜測收成一個量出來的
數字**；第二件是**站立期把腳鎖在世界座標上**（`scripts/player/foot_ik.gd`）。
**射線貼地與法線貼合不做**，等關卡真的出現斜面再說。

**理由**：

1. **主因不是缺 IK，是算術。** 全專案有三個數字在猜同一件事——這支走路片段
   原本對應多快的移動速度：`WALK_REFERENCE_SPEED` 猜 1.6、腳步聲用
   `身高 × 0.62` 反推出另一個、播放倍率上限 1.8 又是第三個。實測
   （`scenes/tools/gait_probe.tscn`）自然速度只有 **0.75–0.92 m/s**，猜的那個
   高了快一倍；而 `SPEED` 是 6.0 m/s，被 1.8 的上限一卡，全速時動畫只跑到
   需要的三成多，其餘全部變成腳在地上滑。**那個量級 IK 修不掉。**
2. **貼地在這個關卡沒有用。** `test_arena.tscn` 與 `camp.tscn` 裡每一個碰得到
   的面都是軸對齊的 `BoxShape3D`，全專案 `.tscn` 沒有任何非 Y 軸旋轉，
   `get_floor_normal()` 一次都沒有被呼叫過。沒有斜面可貼。做了也看不出差別，
   而它會把物理查詢帶進修改器堆疊——那是這個專案目前完全沒有的東西。
3. **步幅沒有調整空間了。** 走路的腳踝前後行程 0.53 公尺、髖到踝的腿長也是
   0.53 公尺，比值 0.99；兩腿伸直的極限大約 1.4。`RUN_STRIDE` 1.45 乘下去
   剛好頂到。所以**衝刺買的是姿勢不是步幅，全速那一段只能靠步頻**
   ——大頭身角色的腿只有身高的三分之一，這是算出來的結果不是動畫的毛病。

**不用 `TwoBoneIK3D`**：Godot 4.7 內建了它，但在這個版本解不出來（自己搭三根
骨頭做最小測試，踝關節完全不動，`influence` 也沒反應；它的文件是整份空的）。
改用自己寫的 CCD——只有兩根骨頭，而且 CCD 從動畫姿勢開始迭代，膝蓋方向
不必額外指定，不會反折。

**踏地的判準是「世界空間速度最慢的那一隻腳」**，不是高度門檻，也不是
「比較低的那一隻」。前兩種都試過而且都壞了：三隻的腳踝離地高度差 0.2 公尺，
高度門檻算出來的站立佔比從 0.32 到 0.65；而「比較低的那一隻」在整個擺盪期間
也還是比較低的，鎖定從來不放開，腳滑反而惡化到 35%。物理上的定義才是對的：
**踏在地上的腳不會動。**

**驗收**：`gait_probe` 的第二段。承重腳滑掉走過距離的百分之幾，理想 0%。
加 `--ik=0` 印出關掉鎖腳的對照組。

## TD-14・手部 IK：穩定持械手用 IK，副手上武器靠姿勢，IK 只收尾

**決定**：手部分兩件事處理，而**兩件的主力剛好相反**。

1. **武器亂甩**——`scripts/player/hand_ik.gd`。把持械手的姿勢換算到角色空間做
   指數平滑，往那個「安靜的姿勢」插值：位置用 CCD 解，**朝向直接寫到手骨上**。
2. **副手握上武器**——**主力是姿勢**（`MotionClips.IDLE`）**不是 IK**。IK 只負責
   收最後幾公分，搆不到就按比例淡出，不硬拉。

解算器抽成 `scripts/player/limb_ik.gd`，與 `foot_ik.gd` 共用（TD-13）。

**理由**：

1. **朝向才是主導畫面的東西，不是位置。** 武器尖端離手掌 0.5–1.0 公尺，手腕
   轉十度尖端就走十幾公分。實測走路時貓的弓尖端一個循環掃過 107 公分，而且
   96 公分在前後方向。**只解位置的話這個數字幾乎不會動**——這是與腳最大的
   差別（腳掌上沒有掛一公尺長的東西，所以 `foot_ik` 不寫朝向）。
2. **副手構不到不是 IK 能解的。** 量之前副手離武器 64–115 公分，而手臂只有
   52–57 公分。IK 在那個距離只能把手臂拉直，看起來比沒接上更糟。所以順序是
   **姿勢先把武器帶到臂長之內，IK 才有事情做**——`hand_probe` 印的
   「肩到握點 ÷ 臂長」就是這件事的判準，超過 1.0 就是姿勢的問題不是 IK 的問題。
3. **哪一把武器要雙手握是武器的性質，不是角色的偏好**，所以寫在
   `WeaponRack.OFF_GRIPS` 而不是名冊。零件表改了握點就該跟著改，放在同一個
   檔案才不會各走各的；而「這張表裡有沒有這把武器」本身就是開關——劍不在
   表上，所以豬維持單手，順便讓有／沒有副手兩條路都被真的走過。
4. **CCD 對大幅度修正收斂得很慢。** 逐輪印殘差量到的：修正 50 公分以內三輪
   就進到 0.02 公分，但修正 85 公分時每一輪只削掉 7%（八輪還差 13 公分）。
   所以 `LimbIk.solve()` 多一個 `reach_first`，先由根往末端掃一遍讓整條鏈朝向
   目標。**腳不開這個選項**：一次落腳只差幾公分，而且由根往末端掃是大腿先動，
   那正是 `foot_ik` 選擇反方向要避開的事（膝蓋方向）。

**`RUN_ARM_SWING` 沒有被刪掉**，雖然本來要刪。它存在的唯一理由就是壓武器，
而這一層已經逐手逐幀在做同一件事——但量了才知道不行：把它與
`SPRINT_ARM_SWING` 都放成 `RUN_STRIDE` 之後，即使 IK 開著，尖端行程還是掉到
跑步 35/33/48 公分（留著是 24/23/31），而且蛙的副手剛好頂到 1.00 倍臂長。
**它與 IK 是相加的，不是二選一。**

**`BoneAttachment3D` 看得到修改器的輸出**，這是整個作法成立的前提，做之前先
驗過：把手骨在修改器裡抬高 0.5，掛點跟著走到同一個位置（0.4899 → 0.9899），
而從堆疊外面讀 `get_bone_global_pose()` 兩次都是 0.4422（還原後的動畫姿勢）。
所以武器會跟著 IK 走，而**任何從外面讀骨頭的東西都讀不到這一層**——弓弦因此
不能自己去讀，要由 `HandIk.draw_point` 發佈。

**弓弦被拉開**（`scripts/player/bow_string.gd`）：弦改成兩段，搭箭點跟著右手跑。
驅動來源是**右手實際的位置**，不是另一條時間軸——不然調了攻擊片段的手臂角度
而忘了調弦，弦會在手還沒到位時先彈回去。這與腳步聲跟動畫共用
`CharacterVisual.step_length()` 是同一招。

**驗收**：`hand_probe` 兩張成績單（尖端行程、副手離握點），`--ik=0` 是對照組。
`beat_probe` 多一條：宣告了雙手握的武器，待機時副手離握點要小於 0.10 倍臂長。

## TD-15・身體起伏用腿的幾何算，走路與跑步相位相反；待機靠三件小事

**決定**：新的一層 `scripts/player/gait_bob.gd` 每幀寫 Hips 的位置（`rest + offset`，
絕不累加），掛在 `RagdollRecovery` 之後、`FootIk` 之前。振幅從兩腳前後距離與腿長
算：`drop = L − √(L² − (d/2)²)`。走路乘負號往下沉，跑步繞平均值上下。`FootIk`
的踏地腳多撐回**剛好**這一層壓下去的量。待機時同一層改做換腳承重，
`ProceduralPose` 加偶爾看旁邊、呼吸振幅放大三倍。

**理由**：

1. **走路片段裡髖根本沒有動。** 9–11 條位置軌全是單格、範圍 0.000。腳不滑、武器
   不甩之後還像素材套上去，這是主因——身體像放在軌道上滑。
2. **振幅要從幾何來，相位才會對。** 猜一個正弦振幅還要另外猜相位，而相位錯了
   比沒有更糟（腳落地時身體反而抬起來）。兩腳分開的距離本身就決定髖能撐多高，
   相位是附送的。
3. **走路與跑步相位相反是物理，不是口味。** 走路是倒單擺（雙支撐時最低），跑步
   是彈簧（騰空時最高、中站立期壓縮）。同一個幾何量，換一個正負號。
4. **走路只能往下沉。** 這支片段的腿本來就快打直（行程／腿長 0.99），往上抬會把
   腳帶離地面。跑步的騰空往上抬時腳離地是對的。
5. **踏地的腳撐回去的量必須剛好等於髖沉下去的量。** 第一版鎖「踩下去時的高度」，
   動畫本身的腳在站立期也會往下踩幾公分，全被撐起來之後 reach clamp 一介入水平的
   鎖就丟了——起伏層還沒開，貓的腳滑就從 5% 惡化到 15%。改成從 `GaitBob.sink`
   讀，數字回到 4.2/4.7/4.9%。**只撐不拉**：跑步騰空時腳本來就該離地。
6. **待機的呼吸原本看不見。** 0.6–1.4 度讓頭動不到半公分，遊戲鏡頭下是雕像。放大到
   2–3.6 度、每 4–7 秒換腳承重、每 3–7 秒看一下旁邊之後，站 8 秒頭動 5–6 公分。

**`HandIk.STEADY_SHARE` 從 0.8 降到 0.6**：0.8 讓劍在走路每一格一模一樣。`hand_probe`
掃過 0.8／0.6／0.5 與兩個時間常數，0.6 落在原始行程的四到五成，圖上劍跟著步子
輕擺。起伏層排在手部 IK 前面，髖的起伏會被平滑吃掉一部分——那就是武器的慣性。

**驗收**：`gait_probe` 多印髖起伏、髖左右、待機 8 秒的頭位移，`--bob=0` 是對照組；
腳滑那組不准變差超過半個百分點。
