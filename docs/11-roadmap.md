# 開發里程碑與範圍規劃

## 現實檢視

每週 15 小時 = 每年約 **780 小時**。

| 範圍 | 估計工時 | 以每週 15 小時計 |
|---|---|---|
| 目前 GDD 的完整範圍 | 約 3,000–4,500 小時 | **4–6 年** |
| 建議的上市範圍（見「範圍取捨」） | 約 1,500–1,800 小時 | **約 2 年** |

這不是要你放棄任何東西，而是決定**哪些先做、哪些等上市後再補**。被砍的內容不會消失，它們變成更新計畫。


## 範圍取捨

### 上市版本必須有（Must）

| 項目 | 理由 |
|---|---|
| 線上三人連線 | 這是遊戲的定義，沒有它就不是這款遊戲 |
| 抓取、投擲、疊高 | 核心動詞 |
| Ragdoll 與倒地救援 | 核心賣點與失敗規則 |
| 3 隻可玩動物（豬、蛙、貓） | 三種功能類型各一，玩法完整 |
| 3 個章節 | 教學章 + 主軸章 + Boss 章 |
| 合體技（圖騰形態） | 情感與戰鬥的高點 |
| AI 夥伴 | 沒有它，湊不到三人的玩家無法遊玩＝差評來源 |
| 誤傷開關 | 低成本、高辨識度 |

### 上市後更新（Should）

| 項目 | 估計工時 | 備註 |
|---|---|---|
| 本地分屏 + 動態分屏 | 300–450 小時 | **本專案成本最高的單項**。渲染兩次、UI 另做一套、混合連線架構 |
| 第 2、4 章 | 每章 200–280 小時 | |
| 海狸、長頸鹿、雞 | 每隻 80–150 小時 | 含模型、動畫、能力、對應謎題 |
| 外觀收集品 | 60–100 小時 | |

### 這一版先不做（Won't）

- 營地建造系統（已定為無數值功能，可簡化為固定場景）
- 新周目
- 成就以外的元數據系統

> **關鍵建議：本地分屏移到上市後。** 它是單項成本最高的功能，而且它的價值（沙發合作）在你只有三章內容時無法充分發揮。先把遊戲做出來，再讓它能兩人同螢幕。


## 里程碑

### M0・技術驗證原型

**目標**：證明這個遊戲在技術上做得出來。全部用膠囊體，零美術。

| 項目 | 內容 |
|---|---|
| 產出 | 三個膠囊在連線下能移動、跳、互抓、投擲、疊高、ragdoll 倒地、被扶起 |
| 驗收標準 | 三台機器連線，疊成三層走動 30 秒不崩、不抖、不穿模，**且在 80–150 ms 延遲 + 1% 丟包下重跑一次仍通過**（見〈[技術決策](13-tech-decisions.md)〉TD-10） |
| 估計工時 | 120–180 小時 |
| 預估期間 | 2–3 個月 |

**必須在此階段撞牆的風險**：玩家站在玩家頭上的網路同步。這是全專案最高風險，若在此失敗，整個設計要重新想。

**Claude 可協助**：Godot 連線架構、疊高的 authority 與插值邏輯、PhysicalBone3D ragdoll 設定、抓取狀態機。

**架構前提**：M0 的工作切分與各項技術決定見〈[技術決策](13-tech-decisions.md)〉。其中 TD-04（`PlayerSlot` 抽象）必須在寫第一行連線程式碼前就位——它是本地分屏、AI 補位、營地換角三項功能的共同前提，事後補裝會動到連線核心。

---

### M1・手感原型

**目標**：回答「這好不好玩」。仍可用簡易美術。

| 項目 | 內容 |
|---|---|
| 產出 | 三段連擊 + 情境攻擊、打擊感規格全部實作、泥偶敵人、一個 5 分鐘的測試場地 |
| 驗收標準 | **找三個朋友玩 20 分鐘，他們自己笑出來，而且問「還有嗎」** |
| 估計工時 | 150–200 小時 |
| 預估期間 | 2.5–3.5 個月 |

**這是整個專案最重要的檢查點。**如果朋友沒笑，不要往下做——回頭調手感，或者承認這個設計需要改。在這裡放棄的成本是 300 小時，在 M3 才發現的成本是 1,500 小時。

**Claude 可協助**：頓幀與鏡頭震的實作、擊退曲線、敵人 AI、攻擊狀態機。

---

### M2・垂直切片

**目標**：第三章完整可玩，品質等同最終產品。

| 項目 | 內容 |
|---|---|
| 產出 | 第三章全內容、三隻角色的完整能力與美術、圖騰與合體技、HUD、音效、AI 夥伴 |
| 驗收標準 | 可以給陌生人玩完不需你在旁邊解說；可以剪出 Steam 預告片 |
| 估計工時 | 400–500 小時 |
| 預估期間 | 6–8 個月 |

**為什麼是第三章**：它同時包含物理解謎、載具、圖騰解鎖、合體技解鎖、致命魚河的多解法設計——一章打包了整個遊戲的賣點。

**此階段同時要做**：Steam 商店頁上架（願望清單越早開始累積越好）。

**Claude 可協助**：關卡資料結構、謎題邏輯、AI 夥伴行為樹、AnimationTree 狀態機、Blender 批次處理腳本、HUD 實作。

---

### M3・內容量產

**目標**：補上第一章與 Boss 章。

| 項目 | 內容 |
|---|---|
| 產出 | 第一章（教學）、第五章（Boss 戰三階段） |
| 驗收標準 | 從頭到尾可以完整通關 |
| 估計工時 | 450–550 小時 |
| 預估期間 | 7–9 個月 |

**風險**：Boss 戰是全新的戰鬥設計，不能沿用小怪邏輯，容易超支。建議在 M2 結束時先做一個 Boss 的紙上原型。

---

### M4・打磨與平衡

| 項目 | 內容 |
|---|---|
| 產出 | 難度平衡、連線穩定性、Bug 修復、教學流程優化、選項與設定 |
| 驗收標準 | 找 10 組陌生玩家測試，完成率高於七成 |
| 估計工時 | 250–350 小時 |
| 預估期間 | 4–5 個月 |

**不要低估這一階段。**多人連線遊戲的打磨成本通常被嚴重低估，尤其是「兩個朋友連不上線」這類問題會直接變成退款。

---

### M5・上市準備

| 項目 | 內容 |
|---|---|
| 產出 | Steam 頁面完稿、預告片、Demo（建議用 M2 的垂直切片改）、本地化、成就 |
| 估計工時 | 120–180 小時 |
| 預估期間 | 2–3 個月 |


## 時程總覽

| 里程碑 | 工時 | 累計期間 |
|---|---|---|
| M0 技術驗證 | 150 | 第 3 個月 |
| M1 手感原型 | 175 | 第 6 個月 |
| M2 垂直切片 | 450 | 第 13 個月 |
| M3 內容量產 | 500 | 第 21 個月 |
| M4 打磨 | 300 | 第 26 個月 |
| M5 上市準備 | 150 | 第 28 個月 |
| **合計** | **約 1,725 小時** | **約 2 年 4 個月** |

> 這是**順利的情況**。單人開發專案普遍超支 30–50%，實際抓 3 年比較安全。


## 每個階段最可能殺死專案的事

| 階段 | 風險 | 對策 |
|---|---|---|
| M0 | 疊高的網路同步做不出來 | 最先做，不要留到後面 |
| M1 | 做出來不好玩，但捨不得承認 | 用「朋友有沒有笑」當客觀標準，不用自己的感覺 |
| M2 | 美術資產無底洞 | 共用骨架、共用動畫、Meshy 流程標準化（見〈美術管線〉） |
| M3 | 內容量產期倦怠 | 這是單人開發最常見的死因。M2 結束就上 Steam 頁面，用願望清單數字當燃料 |
| M4 | 低估打磨成本 | 已在上表預留 300 小時，不要挪用 |


## 分工

### Claude 可以做

- Godot 程式碼（連線、狀態機、AI 行為、UI、shader）
- Blender Python 批次腳本（骨骼重命名、骨架對齊、清理、匯出）
- 檢查 Meshy 匯出檔（骨架階層、命名、面數、材質）並指出問題
- 關卡資料結構與謎題邏輯
- 設計文件維護、範圍評估、技術方案比較

### Claude 不能做

- 在 Godot 編輯器裡操作
- 美術、模型、貼圖、音樂、音效
- 實際試玩、判斷手感
- 發行、行銷、社群

**結論**：實際人力仍為 1 人。Claude 能提高每小時的產出，但不會成為第二個開發者。上表的工時估計已假設有 Claude 協助。


## 下一步

**立即可做**：

1. 確認 Godot 版本（`project.godot` 標的是 4.7）
2. 開始 M0——照〈[技術決策](13-tech-decisions.md)〉的工作切分做，先做 `NetworkService` 與 `PlayerSlot`，再做三個膠囊的連線移動同步，不要碰美術
3. 美術管線驗證：拿**一隻**模型跑通 Meshy → Blender → Godot，產出規格與腳本後回到 M0。這是排除風險，不是美術製作——「M1 前所有美術都是暫時的」這條原則不變

**M1 結束前必須決定**：第三章的海狸與上市範圍衝突（見〈[待決事項](OPEN-QUESTIONS.md)〉）。

**建議先不要做**：任何美術資產的正式製作。在 M1 通過「朋友有沒有笑」的測試之前，所有美術都應該是暫時的。
